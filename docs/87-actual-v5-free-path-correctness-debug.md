# Actual-inference v5 free-path correctness 조사

> 최초 관측: 2026-08-13 07:57 KST
>
> 상태: 원래 v5와 v5r1의 두 correctness 실패를 폐쇄했다. 속도 결과 artifact는
> 한 번도 공개되지 않았으며, v5r1의 추가 CPU 전수 감사로 MPS backend 수치 오차를
> 모델/runtime 의미 불일치와 분리했다.

## 문제 정의

- 기대: free-running parallel-prefill + incremental-cache logits가 같은 실제 checkpoint의
  sequential/full oracle과 사전 고정 tolerance 안에서 일치하고, 모든 위치의 argmax가
  정확히 같아야 한다.
- 실제: `session-01`이 약 45분 실행된 뒤 `_verify_free_bundle()`의 parallel-vs-sequential
  비교에서 `actual timing equivalence argmax differs`로 중단됐다.
- 심각도: publication timing blocker. 이 상태에서는 latency 결과를 만들거나 해석하지
  않는다.
- 결과 노출: runner는 failure 전에 receipt/timing/output artifact를 publish하지 않았다.
  남은 `.active` sentinel SHA-256은
  `acf1ba409e708bee54cb4c1b163f8f6cc0058b913ca11c0a9de4b6b5902d8152`다.
- 고정 plan: `0a404c22010d83026869a07f3e29b772ef5c5b2081fcc6c757cb61b42b66c8f1`.

## 재현 환경

- Mac16,7 / Apple M4 Pro / 48 GiB / macOS build 25F84
- Python 3.13.11, PyTorch 2.13.0, MPS
- session-01 seed 실행 순서: 1729, 31415, 2718, 65537, 57721
- 실패 commit: `075e39d1c671e3f0b8167dbe6c4cc18b0b9458b0`

## 가설

- [x] H1 기각: free verifier의 prompt/generated 위치 정렬에 off-by-one이 있다. 동일 logits를
  잘못된 sequential 위치와 비교하는지를 최소 trace로 확인한다.
- [x] H2 확인: 위치 정렬은 맞지만 MPS parallel-prefill cache와 sequential cache가 near-tie에서
  tolerance 이내 수치 차이로 서로 다른 argmax를 낸다. 실패 위치의 top-2 margin과
  normalized tolerance ratio를 기록한다.
- [x] H3 기각: free-generated byte 경로에서만 boundary/cache state가 controlled continuation과
  달라지는 실제 incremental runtime 결함이 있다. 같은 byte stream의 boundary trace,
  cache diagnostics, full/sequential/parallel logits를 대조한다.

## 원인

free verifier의 위치 정렬이나 boundary/cache transition 오류가 아니다. PyTorch MPS에서
같은 checkpoint와 같은 observed byte stream을 parallel-prefill cache와 sequential cache로
평가할 때, seed 2718 C86의 case 46 생성 위치 20에서 다음 두 byte의 logit이 사실상
동률이었다.

- parallel top-1/2: byte 130 / 160, margin `9.5367431640625e-07`
- sequential top-1/2: byte 160 / 130, margin `4.76837158203125e-07` (첫 grid 재현)
- 최대 logit 절대 오차: `2.86102294921875e-06`
- 사전 고정 `atol + rtol * abs(reference)` 대비 최대 비율: `0.05935319885611534`
- UTF-8 state: continuation 두 개가 남고 허용 범위가 128–191이므로 두 byte 모두 유효

즉 logits 전체는 사전 고정 허용오차의 약 5.9% 안에서 일치하지만, top-2 margin보다 작은
MPS 수치 차이가 exact argmax 순서를 뒤집었다. Exact argmax equality는 이 경우 모델 경로의
의미 있는 불일치가 아니라 허용오차 안에서 순서가 결정되지 않는 numerical tie를 실패로
분류한다.

## 해결 및 예방

기존 v5 plan과 실패 sentinel은 성공 evidence로 재사용하지 않는다. 새 revision은 다음을
동시에 요구한다.

1. 모든 logits가 기존 bitwise-independent allclose gate를 그대로 통과한다.
2. argmax가 다르면 두 선택의 logit interval이 기존 tolerance 아래 실제로 겹쳐야 한다.
3. exact와 tie-ambiguous comparison 수를 별도로 기록하고 합이 모든 비교 위치와 같아야 한다.
4. tie interval이 겹치지 않는 stable argmax mismatch는 계속 hard failure다.
5. 실제 timed parallel path가 생성한 masked greedy byte와 저장 output은 계속 exact match여야 한다.

이 변경은 timing workload, 모델 pair, case, repetition, 통계 단위 또는 10% 효율 gate를
바꾸지 않는다. 속도 artifact가 하나도 공개되지 않은 상태에서 revision을 먼저 Git에
봉인한 뒤 다섯 fresh-process session을 처음부터 다시 실행한다.

## 후속 실행 상태

V5r1의 첫 실행 시도는 model work가 시작되기 전에 Mac이 AC에서 배터리 전원으로
전환되어 환경 적격성 gate에서 중단됐다. Timing/output/session receipt는 생성되지
않았고, 제외 사유와 당시 전원·thermal 상태만
`results/phase3-inference-actual-v5r1/failures/session-01-attempt-01.json`에 봉인했다.
따라서 이 시도 역시 latency 표본이 아니며, 다섯 eligible session은 AC 전원에서 새
fresh process로 시작한다.

## v5r1 두 번째 실행: MPS shape-dependent tolerance 초과

AC 전원이 복구된 뒤 v5r1 session-01을 다시 시작했지만, timing loop 이전의 controlled
correctness gate에서 seed 65537 C86 reference의 case 66이 중단됐다. Sequential-cache와
full-main logits의 argmax는 동일했지만 `(observed position=126, logit=17)` 한 원소가 기존
허용범위를 약 5.1% 넘었다.

- MPS 절대 logit 오차: `2.1284446120262146e-05`
- 기존 tolerance 대비 비율: `1.0507920980453491`
- argmax: 양쪽 모두 byte `93`
- 최대 probability 절대 오차: `1.1920928955078125e-07`
- 해당 row probability total variation: `1.172570307739428e-07`
- 같은 checkpoint/case의 CPU 비율: `0.4326504170894623`, argmax 동일

이 실행도 timing/output/session receipt를 전혀 publish하지 않았다. 실패 active sentinel은
SHA-256 `873777236cce5eb7918b59b288fe66bd5bb42d3cb232acd5fcf0a7be1c9e8a7b`로
기록한 뒤 폐쇄했으며, 상세 receipt는
`results/phase3-inference-actual-v5r1/failures/session-01-attempt-02.json`이다.

### CPU 전수 감사

같은 5 seeds × candidate/reference 2 roles, 동일 72 controlled cases를 CPU에서 원래
`atol=2e-5, rtol=2e-5` 계약으로 모두 재생했다. 10/10 bundle이 통과했고 모든 비교의
argmax가 정확히 같았다.

이 결과는 boundary/cache semantics가 깨졌다는 설명과 맞지 않고, MPS에서 서로 다른 tensor

설명과 일치한다. 따라서 다음 revision은 원래 CPU semantic oracle을 유지하고, MPS에서는
별도의 보수적 backend envelope와 probability-distribution/greedy-output 불변식을 함께
검사한다. 모델 pair, case, timing workload, repetitions, 통계량, 10% 효율 gate는 바꾸지 않는다.

### v5r2 사전 고정 acceptance contract

전체 MPS grid를 다시 보기 전에 다음 round-number bound를 고정한다.

1. 각 fresh session에서 5 seeds × 2 roles의 72 controlled cases를 CPU로 독립 재생하고,
   기존 `atol=2e-5, rtol=2e-5`를 그대로 통과해야 한다.
2. MPS의 full/sequential/parallel 비교에는 backend safety envelope
   `atol=1e-4, rtol=2e-5`를 사용한다. 기존 tolerance 비율과 초과 원소 수는 별도
   diagnostic으로 모두 보존한다.
3. 모든 비교 row의 softmax probability total variation은 `<=1e-5`여야 한다. 이는 두
   분포 사이에서 이동한 총 확률 질량을 0.001 percentage point 이하로 제한한다.
4. Argmax는 exact이거나 safety-envelope interval이 겹치는 numerical tie여야 한다.
   실제 timed MPS path가 낸 strict-mask greedy byte는 저장 output과 계속 exact여야 한다.
5. CPU semantic oracle, MPS safety envelope, probability TV, boundary/cache, greedy 중 하나라도
   실패하면 tolerance를 세 번째로 완화하지 않고 actual-efficiency gate를 실패로 닫는다.

`1e-4`와 `1e-5`는 관측 최대값에 작은 epsilon을 더한 값이 아니라 각각 logit safety와
probability-mass 보존에 둔 보수적인 decimal bound다. 이 계약을 먼저 Git에 고정한 뒤
전체 MPS bundle을 correctness-only로 감사하고, 통과할 때만 v5r2 실행 코드를 완성한다.

## v5r2 plan 이후 dry-run device identity 실패

v5r2 plan을 봉인한 뒤 장시간 session 전에 seed 65537 C86 case 66 하나를 실제 새 코드로
CPU/MPS 재생했다. CPU oracle은 통과했지만 MPS 비교 전에 device/contract guard가
`ValueError`로 중단됐다. PyTorch는 `model.to("mps")` 뒤 parameter device를 `"mps:0"`로
정규화하는데, 새 guard가 literal `"mps"`만 허용한 구현 오류였다. 기존 `_synchronize()`도
같은 literal 비교를 사용해 `mps:0`을 놓칠 수 있었다.

이 dry run은 timing session이 아니며 timing/output/receipt를 만들거나 latency를 열지 않았다.
V5r2 plan은 성공 evidence로 재사용하지 않고
`results/phase3-inference-actual-v5r2/failures/preflight-device-identity.json`으로 폐쇄한다.
후속 revision은 device family를 `startswith("mps")`로 판정하고 실제 synchronization을
검증하는 실행-only 수정이다. CPU/MPS tolerance, TV, model pair, cases, workload, statistics,
10% gate는 바꾸지 않는다.
